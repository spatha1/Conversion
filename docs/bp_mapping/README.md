# BP Conversion — Field Mapping & Gap Analysis

**Scope:** every field in every XML template of the BP (Business Protection) conversion pipeline,
traced end to end — DCT target path → conversion token → view logic → staging rules → raw Pure
(PRD_T5) source — mirroring the PP methodology (`docs/pp_mapping/`). **Gaps are established from
code, live data, and the BP PL101 mapping spec** (`files/pl101/Conversion_Mapping_BP_PL101_V2.xlsx`)
where PP used `docs/PL101_FieldReference.html` (that file is PP-only — BP has no equivalent single
HTML reference; the xlsx is the ground truth here).

**No HTML deliverables for BP** — Markdown gap cards + `.sql` fix drafts only, per the brief.

## Full-67-config mechanical sweep (2026-07-09)

Extended the original hardcoded-Indicator sweep (which only checked seqs already touched by the
indicator-fix batch) across **all 67 active `ConversionConfig` rows** — every SEQ ID's template
pulled live from Azure, tokens extracted, cross-checked against its source view's actual Snowflake
columns. Three checks run:

1. **Unresolved tokens** (`{TOKEN}` in template with no matching column in the source view — PP's
   G-28 pattern). **Result: 0 across all 67.** BP does not have this class of bug — clean pass,
   no gap. Every token that appears in a BP template does resolve to a real column.
2. **Hardcoded `Indicator=0`** (inverse of the original `Indicator=1` sweep, not previously
   checked). **Result: 1 instance** — G-BP-49.
3. **Empty self-closing tags** (`<Field/>` with no token at all — the pattern that found SEQ 67's
   FuelType/PowerKW/TrackRear gap). **Result: present in 14 of 67 configs**, ranging from 1 empty
   field (SEQ 8, 35, 47, 51, 54) up to **SEQ 61's ~110 empty fields** — see G-BP-48, by far the
   largest single finding in this register. Every occurrence was checked against its view's actual
   column list before being counted as a real gap (several "empty" fields — Excess sub-elements,
   ClassCode wrapper fields — are legitimately always-blank by XML structure, not gaps; those were
   filtered out and are not listed).

This sweep is mechanical (regex + `INFORMATION_SCHEMA` cross-check), not the full manuscript+SAS
methodology — it's a triage pass to make sure the register doesn't miss anything before the
one-by-one deep dive starts, the same way the original 17-seq indicator sweep was a triage pass
before this register existed.

## Cross-cutting patterns (worth fixing as classes, not one-offs)

1. **Hardcoded `Indicator=1` while a real indicator column already exists in the view but was never
   wired into the ConversionConfig template** — originally grouped as one class (G-BP-18, G-BP-20,
   G-BP-22 through G-BP-31, 12 instances). Per-SEQ verification (2026-07-11) split this into two
   real sub-classes: (a) **line-level "is this coverage taken" indicators** (G-BP-18's DFW/STB/STD/CCC_SD
   line-level companions, G-BP-20, G-BP-22) turned out to be **correct-by-design** every time — the
   staging table only ever contains rows where the line is already taken, so the "real column" is
   trivially always 1 and wiring it in changes nothing; (b) **sub-coverage-specific indicators driven
   by a genuine per-policy flag** (G-BP-18's actual bug — `ProtectionTypeStandard`, 11% variance) are
   real bugs. Don't assume every hardcode in this shape is a bug — check whether the "real column" the
   fix would wire in actually varies in live data before scripting a fix. G-BP-23 through G-BP-31 not
   yet re-verified against this finding. Same class PP found (its cross-cutting pattern #2).
2. **PL101-documented default/banding rules not matching the live view's hardcoded fallback** —
   G-BP-01 (NZ Theft), G-BP-02 (NZ Landslide), G-BP-03 (NZ Flood), G-BP-04 (Money banding). All four
   found by the same method: cross-checking a live view's `CASE`/default logic against the actual
   PL101 row for that field, rather than assuming the fallback was intentional.
3. **Underwriting Adjustments failing to populate across multiple, unrelated coverage screens** —
   G-BP-14 (BG/BI/EN/Money all reported independently in 2026-06-26 test execution). PP found an
   analogous single-root-cause pattern (PR-04) — worth checking `SAS/txt/` for a shared BP UW
   Adjustment block the same way, before treating these as 4 separate gaps.
3. **Silent staging-level data loss via dedup/join, invisible at the view layer** — G-BP-06 (CM
   vehicle dedup drops schedule clauses + UW answers), G-BP-38 (schedule clause template, likely same
   root cause), G-BP-16 (Additional Interest dropped records, unconfirmed same class). None of these
   show up as a "wrong value" in any view — the row simply never arrives with its full data. Not
   caught by the config/view-level indicator sweep that found the other 30 gaps; found by comparing
   row counts before/after a staging join instead.
4. **Raw Pure value passed straight to DCT with no CASE translation at all** (not a mapping gap —
   no mapping exists) — G-BP-08 (ImportType), G-BP-11 (VehicleType ELSE), G-BP-13 (FL HighestRiskUse).
