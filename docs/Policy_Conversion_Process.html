Policy Conversion Process

BP & PP Lines of Business — Legacy to Duck Creek (DCT) via SWIFT Conversion

Document type: Process Overview Teams: Aggne & SOIC (Capricorn — Client) Version: 1.0 Date: 02 July 2026

1Overview

The Policy Conversion process migrates in-force Business Protection (BP) and Personal Protection (PP) policies from the legacy system into the Duck Creek (DCT) policy system. The Aggne team runs conversion batches through the SWIFT Conversion engine, generates policy payloads, and submits them to DCT. Every batch is validated; issues found are analysed, classified, and routed to the right owner — data issues to SOIC (Capricorn, the client) and implementation issues to the Aggne development team — then fixed and re-run in the next batch. The cycle repeats until all policies are converted and stable.

Batch-driven

Conversion runs as repeatable batches. Each run picks up the latest policy transactions, so fixes and fresh data flow together.

Validated at every gate

Payloads are validated before and after submission to DCT. Nothing is considered converted until DCT accepts it.

Clear issue ownership

Every failure is classified once and routed once — client data questions to SOIC, code and configuration fixes to Aggne.

Daily transparency

A daily report shows converted policy counts, pass/fail results, and open issues for both teams and management.

2End-to-End Process Flow

Aggne team lane SOIC (Capricorn — Client) lane Validation gate Data issue path Implementation issue path
Key principle: the process is a closed loop. Every issue — whether resolved by SOIC inputs or an Aggne fix — feeds the next batch run, which picks up both the corrections and the latest policy transactions from the legacy system.

3Batch Execution Steps

#StepDescriptionOwner
1 Extract from Legacy Policy data for the batch is collected from the legacy system (Pure), including the latest renewal and endorsement transactions since the previous run. Aggne
2 Run SWIFT Conversion The batch is processed through the SWIFT Conversion engine, which transforms legacy policy data into the DCT target structure. Aggne
3 Validation Gate Converted output is validated against mandatory-field, format, and business rules. Policies that fail move directly to analysis; passing policies continue. Aggne

5 Submit to DCT — Request / Response Payloads are submitted to the DCT system. Each response is captured: valid responses mean the policy is created in DCT; invalid responses are queued for analysis. Aggne
6 Analysis & Classification The Aggne team analyses every failed validation and invalid DCT response, and classifies each as a Data Issue or an Implementation Issue (see Section 4). Aggne
7 Resolve & Re-run Once SOIC inputs are received and/or Aggne fixes are deployed, the next batch is executed. It carries the corrections plus the latest legacy transactions, and the cycle repeats until stable. Aggne SOIC

4Issue Triage & Routing

Every failure is classified exactly once during analysis, then follows one of two tracks:

Data Issue — routed to SOIC

The policy data in the legacy source is missing, inconsistent, or has values the target system does not recognise. Resolution needs a business decision or corrected data from the client.

  1. Aggne prepares a report and analysis — affected policies, fields, and the decision required.
  2. Report is shared with SOIC for review.
  3. SOIC provides inputs to fix / modify — corrected data, an approved default, or a mapping decision.
  4. Aggne applies the inputs and includes the policies in the next batch.

Implementation Issue — handled by Aggne

The conversion logic, mapping, or configuration produced an incorrect result. Resolution is a code or configuration change on the Aggne side.

  1. An ADO work item is created to log the defect with full context.
  2. The Aggne team develops and tests the fix.
  3. The item is tracked until closure — fix deployed and verified.
  4. The corrected logic takes effect in the next batch run.
Closure criterion (both tracks): an issue is closed only when the affected policies pass validation and are accepted by DCT in a subsequent batch — not when the fix or input is delivered.

6Reporting

A daily report is produced from the SWIFT Conversion run and shared with both teams. It provides a single view of conversion progress and open items:

Converted policies

Count of policies successfully created in the DCT policy system, by line of business (BP / PP) and batch.

Pass / fail summary

Validation results for the latest batch — policies passed, failed at validation, and rejected by DCT.

Open issues

Outstanding data issues awaiting SOIC input and implementation issues in progress (ADO status).

Trend to closure

Batch-over-batch movement — issues resolved, new issues found, and remaining scope until stabilisation.

7Glossary

SWIFT Conversion
The conversion engine operated by the Aggne team that transforms legacy policy data into the DCT target format and validates it.
SOIC
Capricorn — the client organisation. Owns the legacy policy data and provides business decisions and data corrections for data issues.
Aggne Team
The delivery team responsible for running conversion batches, validating output, submitting to DCT, and fixing implementation issues.
Legacy System (Pure)
The source policy administration system from which BP and PP policies are being migrated.
DCT
Duck Creek — the target policy system receiving the converted policies.
Payload
The structured policy request (XML) generated per policy and submitted to DCT.
ADO
Azure DevOps work item — used to log, track, and close implementation defects.
Batch
One end-to-end conversion run. Batches repeat, each carrying fixes plus the latest legacy transactions, until all policies convert cleanly.
BP / PP
Business Protection and Personal Protection — the two lines of business in conversion scope.
