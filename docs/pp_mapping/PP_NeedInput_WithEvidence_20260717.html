Data (4,362 vehicles): | Value | Count | |---|---| | (blank) | 3,600 | | Other | 661 | | Cab Chassis | 10 |

Question: Has this same BodyType mapping already been solved on the BP (Business Protection) side? If so, we'd like to reuse that precedent rather than invent a new one. If not, what should Other and Cab Chassis map to?

2. NumberOfCylinders — cylinder-less vehicles

Field: NumberOfCylinders (risk/NumberOfCylinders) — Dropdown, required, integers 1–16 only (no 0 or blank option) Currently sent: 0 for 512 vehicles that Pure/RedBook flags as genuinely having no cylinders (trailers, EVs, etc. — RedBook code 11 = "none"). 0 is not a valid dropdown value.

SELECT NUMBEROFCYLINDERS, COUNT(*),
       CASE WHEN NUMBEROFCYLINDERS BETWEEN 1 AND 16 THEN 'VALID' ELSE 'STILL INVALID' END
FROM AGGNE.DEV.PER_COM_PAYLOAD GROUP BY 1 ORDER BY 2 DESC;

Question: For cylinder-less vehicle types, should the NumberOfCylinders tag be omitted entirely, or is there a specific value DCT expects instead of 0?

3. VoluntaryExcess — re-banding above $1,000

Field: VoluntaryExcess (risk/VoluntaryExcess) — Dropdown DCT accepts: 0, 250, 500, 750, 1000, 1250, 1500 (7 PP options) Currently sent: 2000 or 5000 for excess amounts above $1,000 — both outside the valid option list (this banding looks copied from the BP/Business excess rules, which do allow higher bands).

Data: 9 vehicles currently affected. Structurally, the banding logic also never produces 250, 750, or 1250 at all — those three PP options are unreachable today regardless of the 2000/5000 issue.

SELECT VOLUNTARYEXCESS, COUNT(*),
       CASE WHEN VOLUNTARYEXCESS IN (0,250,500,750,1000,1250,1500) THEN 'VALID' ELSE 'STILL INVALID' END
FROM AGGNE.DEV.PER_COM_PAYLOAD GROUP BY 1 ORDER BY 2 DESC;

Question: What should a raw excess amount above $1,000 map to — cap at $1,500 (nearest valid option), re-band more granularly across all 7 options, or a different pricing-driven rule? This is a customer-facing dollar amount, so we don't want to guess.

4. AgeOfYoungestRegularDriver — minimum age threshold conflict

Field: AgeOfYoungestRegularDriver (risk/AgeOfYoungestRegularDriver) — numeric, required Conflict: the current code nulls out any age under 16, on the understanding (documented earlier in this project) that 16 matches DCT's minimum age rule. Re-checking the DCT manuscript directly, the actual minimum is defined as 17, not 16.

Data (3,306 vehicles): 218 blank (6.6%); 2 vehicles currently carry age 16, which passes today's <16 check but would fail DCT's real minimum of 17.

SELECT COUNT(*) AS TOTAL,
  SUM(CASE WHEN COALESCE(TRIM(AGEOFYOUNGESTREGULARDRIVER),'')='' THEN 1 ELSE 0 END) AS AGE_BLANK
FROM AGGNE.DEV.PER_COM_PAYLOAD;

Question: Was 16 a deliberate choice for a reason outside the DCT manuscript (e.g. a local learner-driver age rule), or should the threshold be corrected to 17 to match DCT? We want to confirm before changing a rule that was previously documented as intentional.

5. UW Adjustments — non-recurring adjustments excluded entirely

Field: UnderwritingAdjustment (Home Contents / Motor UW adjustment blocks) Finding: the procedure that builds these blocks only ever selects adjustments flagged recurring in Pure (AJRecurringIndicator = 1). Non-recurring adjustments are filtered out upstream and never reach DCT at all — not sent with a "No" recurring flag, simply absent.

Data: | Source | Recurring (included) | Non-recurring (excluded) | % excluded | |---|---|---|---| | Motor adjustments | 7,686 | 11,450 | 59.9% | | Home Contents/Buildings adjustments | 4,779 | 8,365 | 63.6% |

SELECT AJRecurringIndicator, COUNT(*) FROM PRD_T5_EXTERNAL_AGGNE.PURE_SNAPSHOT.PER_ADJUSTMENTSMV GROUP BY 1;
SELECT AJRecurringIndicator, COUNT(*) FROM PRD_T5_EXTERNAL_AGGNE.PURE_SNAPSHOT.PER_ADJUSTMENTSHC GROUP BY 1;

Question: Is excluding non-recurring UW adjustments from conversion intentional (e.g. one-time historical adjustments genuinely shouldn't carry forward onto a freshly-converted policy), or should they be included? Given this affects roughly 60% of all adjustment records, we wanted to confirm rather than assume either way.

6. Premium double-carry on combined Home Buildings + Home Contents policies

Field: coverage/Premium on both the Home Buildings and Home Contents coverage blocks Finding: on every policy that has both Buildings and Contents cover, both coverage blocks currently carry the exact same total home premium figure, rather than a split between the two.

Data: 1,109 of 1,843 combined policies (60.2%) are affected.

SELECT PUREPOLICYNUMBER, EXPPREM AS HB_PREMIUM, HBEXPPREM AS HC_PREMIUM

Question: Does DCT sum the Premium values across coverage blocks when calculating the policy total? If so, this would double-count the premium on every combined HB+HC policy. Separately — does a genuine Buildings-only / Contents-only premium split exist anywhere in Pure that we should be sourcing instead of the combined total?

How to read this

  • Pure Value = the exact code/text currently sitting in our source data for this clause.
  • Sent to DCT as = what we currently transmit in the payload (today: unchanged pass-through of the Pure Value — no translation happens).

8. Home Buildings — Landlords Protections indicator

Field: coverage/Indicator on the Landlords Protections (LLB_SD) sub-coverage block Finding: DCT expects this Indicator to reflect whether Landlord Protections was actually elected (Taken/NotTaken), but the view currently sends 1 for every policy — there's no Taken/NotTaken status sourced for this block at all today.

Data: as a signal (not a direct measure), 2,097 of 3,054 Home Buildings policies (68.7%) are on Owner Occupied properties yet still show Landlords Indicator=1 — Landlords cover typically wouldn't apply where there's no tenant.

SELECT COUNT(DISTINCT S.PUREPOLICYNUMBER) AS LLB_ON_OWNER_OCCUPIED
FROM AGGNE.DEV.PER_BB_SUBCOVERAGES S
JOIN AGGNE.DEV.Locationdetails_PER L
  ON TRIM(SPLIT_PART(S.PUREPOLICYNUMBER,'|',1)) = TRIM(L.PUREPOLICYNUMBER)
WHERE S.CODE = 'HBLLB_SD' AND L.HOWOCCUPPIED = 'Owner Occupied';

Question: Does Pure carry an explicit "Landlord Protections elected" flag we can source directly? If not, is occupancy type (Owner Occupied → not taken, else → taken) an acceptable proxy, or does that break for other occupancy types (e.g. vacant properties)?

9. Home Buildings UW Adjustments — in scope or not?

16. Motor sub-coverage matrix — which coverages apply to which protection type

Field: coverage/Indicator across the 8 Motor sub-coverage blocks (Comprehensive Property, Choice of Repair, Fire & Theft, Comprehensive Liability, Car Hire, Third Party Fire & Theft, Third Party Only, Unlimited Glass) Finding: all 8 blocks are currently sent with Indicator="on" for every vehicle regardless of the policy's actual protection type.

Data: | ProtectionType | Unexpected block | Count | |---|---|---| | Third Party Only | Comprehensive Property | 230 | | Third Party Only | Choice of Repair | 230 | | Third Party Only | Car Hire | 230 | | Third Party Only | Unlimited Glass | 230 | | Comprehensive (Agreed Value) | Third Party Only | 900 | | Comprehensive (Market) | Third Party Only | 1,801 |

SELECT P.PROTECTIONTYPE, C.CODE, COUNT(*) AS CNT
FROM AGGNE.DEV.PER_COM_COVERAGES C JOIN AGGNE.DEV.PER_COM_PAYLOAD P
  ON C.PUREPOLICYNUMBER = P.PUREPOLICYNUMBER
WHERE (P.PROTECTIONTYPE = 'ThirdPartyOnly' AND C.CODE IN ('PMCMP_SD','PMPCH_SD','PMULG_SD','PMCOR_SD'))
   OR (P.PROTECTIONTYPE LIKE 'Comprehensive%' AND C.CODE = 'PMTPO_SD')
GROUP BY 1, 2 ORDER BY 1, 2;

Question: What's the correct matrix of which of the 8 coverage codes should be "on" for which ProtectionType? Separately, should Car Hire / Choice of Repair / Unlimited Glass also depend on the existing Taken/NotTaken option fields already captured elsewhere on the policy, rather than ProtectionType alone?
